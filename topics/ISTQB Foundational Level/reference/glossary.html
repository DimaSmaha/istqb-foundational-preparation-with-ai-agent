Glossary

Running reference of CTFL v4.0 terms, in the syllabus's own wording. Grows chapter by chapter — every lesson should use these terms consistently with this page.

Source: all definitions are drawn from the "Keywords" lists and body text of ISTQB CTFL Syllabus v4.0.1. Chapter noted after each term.

Chapter 1 — Fundamentals of Testing

Coverage — the extent to which a specified set of coverage items has been exercised by a set of test cases, expressed as a percentage. (§1.4.4)

Debugging — the activity concerned with finding causes of a failure (reproduction, diagnosis, fixing the defect), separate from testing. (§1.1.2)

Defect (fault, bug) — a flaw in a component or system that can cause it to fail to perform its required function, produced when an error touches a work product. (§1.2.3)

Error (mistake) — a human action that produces an incorrect result; the cause of a defect. (§1.2.3)

Failure — an event in which a component or system does not perform a required function within specified limits, typically caused by execution of a defect. (§1.2.3)

Quality — the degree to which a component or system satisfies stated and implied needs of stakeholders. (§1.1)

Quality assurance (QA) — a process-oriented, preventive approach focused on implementing and improving processes; distinct from testing, which is product-oriented and corrective. (§1.2.2)

Root cause — a fundamental reason for the occurrence of a problem, identified through root cause analysis. (§1.2.3)

Test analysis — the test activity that analyzes the test basis to identify testable features and define associated test conditions. Answers "what to test?" (§1.4.1)

Test basis — the body of knowledge used as the basis for test analysis and design (e.g. requirements, user stories, design). (§1.4.4)

Test case — a set of preconditions, inputs, actions, expected results, and postconditions developed to cover a test condition. (§1.4.3)

Test completion — the test activity, occurring at project milestones, that archives testware, hands over useful items, and produces a test completion report. (§1.4.1)

Test condition — a testable aspect of a component or system identified during test analysis. (§1.4.1)

Test control — the test activity that takes the actions necessary to meet test objectives, based on test monitoring information. (§1.4.1)

Test data — data created or selected to satisfy test case input requirements, produced during test implementation. (§1.4.3)

Test design — the test activity that elaborates test conditions into test cases and other testware. Answers "how to test?" (§1.4.1)

Test execution — the test activity that runs tests according to the test execution schedule and compares actual vs. expected results. (§1.4.1)

Test implementation — the test activity that creates or acquires testware needed for test execution (test procedures, scripts, environment). (§1.4.1)

Test monitoring — the test activity that involves ongoing checking of test activities and comparison of actual progress against the plan. (§1.4.1)

Test object — the work product being tested. (§1.1)

Test objective — a reason or purpose for designing and executing a test (e.g. finding defects, building confidence). (§1.1.1)

Test planning — the test activity of defining test objectives and selecting an approach that best achieves them within given constraints. (§1.4.1)

Test procedure — a sequence of test cases in execution order, plus any associated actions. (§1.4.3)

Test process — the set of test activities (planning, monitoring & control, analysis, design, implementation, execution, completion) performed to achieve test objectives. (§1.4)

Test result — the outcome of executing a test, logged for comparison against expected results. (§1.4.1)

Testing — a set of activities to discover defects and evaluate the quality of software work products; includes both static and dynamic activities, and both verification and validation. (§1.1)

Testware — the work products produced during the test process (test plans, test cases, scripts, logs, reports, etc.). (§1.4.3)

Traceability — the degree to which a relationship can be established between the test basis, testware, test results, and defects. (§1.4.4)

Validation — confirmation that a system meets the users' and other stakeholders' needs in its operational environment. (§1.1)

Verification — confirmation that a system meets specified requirements. (§1.1)

Chapter 2 — Testing Throughout the Software Development Lifecycle

Acceptance testing — test level focused on validation and on demonstrating readiness for deployment, i.e. that the system fulfills the user's business needs; ideally performed by the intended users. (§2.2.1)

Black-box testing — a test type, specification-based, that derives tests from documentation not related to the internal structure of the test object; checks the system's behavior against its specifications. (§2.2.2)

Component integration testing (unit integration testing) — test level focused on testing the interfaces and interactions between components; heavily dependent on the integration strategy (bottom-up, top-down, big-bang). (§2.2.1)

Component testing (unit testing) — test level focused on testing components in isolation, normally performed by developers in their development environments. (§2.2.1)

Confirmation testing — confirms that an original defect has been successfully fixed. (§2.2.3)

Functional testing — a test type evaluating the functions a component or system should perform ("what" it should do): functional completeness, correctness, and appropriateness. (§2.2.2)

Integration testing — testing focused on interfaces and interactions, covering both component integration testing and system integration testing. (§2.2.1)

Maintenance testing — testing the changes to an already-operational system, triggered by modifications, environment upgrades/migrations, or retirement. (§2.3)

Non-functional testing — a test type evaluating attributes other than functional characteristics ("how well" the system behaves): performance efficiency, compatibility, usability/interaction capability, reliability, security, maintainability, portability/flexibility, safety. (§2.2.2)

Regression testing — confirms that no adverse consequences have been caused by a change, including an already-confirmed fix, in the changed component, other components, or connected systems. (§2.2.3)

Shift left — the principle of early testing applied as an approach: performing test activities earlier in the SDLC, without neglecting testing later in the SDLC. (§2.1.5)

System integration testing — test level focused on testing the interfaces of the system under test with other systems and external services. (§2.2.1)

System testing — test level focused on the overall behavior and capabilities of an entire system or product, often including both functional and non-functional testing. (§2.2.1)

Test level — a group of test activities organized and managed together, forming an instance of the test process performed in relation to software at a given development phase. (§2.2)

Test object — the work product being tested (used across test levels, from component to system). (§1.1, §2.2.1)

Test type — a group of test activities related to specific quality characteristics; most test types can be performed at every test level. (§2.2)

White-box testing — a test type, structure-based, that derives tests from the system's implementation or internal structure (code, architecture, work flows, data flows); covers the underlying structure to an acceptable level. (§2.2.2)

Chapter 3 — Static Testing

Anomaly — any condition that deviates from expectation, identified by a reviewer during an individual review and logged along with recommendations and questions; not necessarily a defect. (§3.2.2)

Dynamic testing — testing that involves the execution of software; contrasted with static testing, which does not require the software under test to be executed. (§3.1, §3.1.3)

Formal review (see Inspection) — a review type at the most rigorous end of the formality spectrum, following the complete generic review process. (§3.2.4)

Informal review — a review type that does not follow a defined process and does not require a formal documented output; the main objective is detecting anomalies. (§3.2.4)

Inspection — the most formal type of review, following the complete generic process; the main objective is to find the maximum number of anomalies, and the author cannot act as the review leader or scribe. (§3.2.4)

Review — a type of static testing in which a work product is evaluated through manual examination, typically involving stakeholders such as the author, reviewers, moderator, and scribe. (§3.1, §3.2)

Static analysis — a form of static testing performed with the help of a tool (rather than manual examination), used to detect problems prior to dynamic testing without requiring test cases; often incorporated into CI frameworks. (§3.1)

Static testing — testing in which the software under test does not need to be executed; work products are evaluated through manual examination (e.g., reviews) or with the help of a tool (e.g., static analysis). (§3.1)

Technical review — a review performed by technically qualified reviewers and led by a moderator, with objectives including gaining consensus and making decisions regarding a technical problem, detecting anomalies, and building confidence in the work product. (§3.2.4)

Walkthrough — a review led by the author, serving objectives such as evaluating quality, building confidence, educating reviewers, gaining consensus, generating new ideas, and detecting anomalies; an individual review beforehand is not required. (§3.2.4)

Chapter 4 — Test Analysis and Design

Acceptance criteria — the conditions that an implementation of a user story must meet to be accepted by stakeholders; may be viewed as the test conditions that should be exercised by the tests. (§4.5.2)

Acceptance test-driven development (ATDD) — a test-first approach in which test cases are created, prior to implementing the corresponding functionality, by team members with different perspectives (e.g., customers, developers, testers). (§2.1.3, §4.5.3)

Black-box test technique (specification-based technique) — a test technique based on an analysis of the specified behavior of the test object without reference to its internal structure. (§4.1, §4.2)

Boundary value analysis (BVA) — a black-box test technique based on exercising the boundaries of equivalence partitions; used for ordered partitions. (§4.2.2)

Branch coverage — the percentage of branches that have been exercised by a test suite; coverage is measured as the number of branches exercised by test cases divided by the total number of branches. (§4.3.2)

Checklist-based testing — an experience-based test technique whereby a tester designs, implements, and executes tests to cover test conditions found in a checklist. (§4.4.3)

Collaboration-based test approach — a test approach that focuses on defect avoidance through collaboration and communication among different stakeholder perspectives (business, development, testing), as opposed to defect detection alone. (§4.5)

Coverage — the extent to which a specified set of coverage items has been exercised by a test suite, expressed as a percentage. (§1.4.4, §4.1)

Coverage item — an entity or property used as a basis for test analysis or test design, e.g., an equivalence partition, a boundary value, or a decision table's column. (§4.1)

Decision table testing — a black-box test technique used to test the implementation of requirements that specify how different combinations of conditions result in different outcomes. (§4.2.3)

Equivalence partitioning (EP) — a black-box test technique that divides data into partitions based on the expectation that all elements of a given partition are to be processed in the same way by the test object. (§4.2.1)

Error guessing — an experience-based test technique used to anticipate the occurrence of errors, defects, and failures, based on the tester's knowledge, including how the application has worked in the past and what kinds of errors developers tend to make. (§4.4.1)

Experience-based test technique — a test technique based on using the knowledge and experience of testers for the design and implementation of test cases, complementary to black-box and white-box test techniques. (§4.1, §4.4)

Exploratory testing — an experience-based test technique in which tests are simultaneously designed, executed, and evaluated while the tester learns about the test object. (§4.4.2)

State transition testing — a black-box test technique used to test the behavior of a test object modeled as a state diagram or state table, exercising states and transitions. (§4.2.4)

Statement coverage — the percentage of executable statements that have been exercised by a test suite; coverage is measured as the number of statements exercised divided by the total number of executable statements. (§4.3.1)

Test technique — a procedure used to derive and/or select test cases; test techniques are classified as black-box, white-box, and experience-based in this syllabus. (§4.1)

White-box test technique (structure-based technique) — a test technique based on an analysis of the test object's internal structure and processing (e.g., code, architecture, work flows, data flows). (§4.1, §4.3)

Chapter 5 — Managing the Test Activities

Defect management — an established process for handling individual defects or anomalies from their discovery to their closure, comprising logging, analysis, classification, response, and closure. (§5.5)

Defect report — a document reporting a flaw found during testing, typically including a unique identifier, description enabling reproduction, expected and actual results, severity, priority, and status; called an incident report in ISO/IEC/IEEE 29119-3. (§5.5)

Entry criteria — the preconditions for undertaking a given activity; if not met, the activity is likely to be more difficult, time-consuming, costly, and riskier. (§5.1.3)

Exit criteria — what must be achieved to declare an activity completed, e.g. measures of thoroughness or binary "yes/no" criteria; called Definition of Done in Agile software development. (§5.1.3)

Product risk — a risk related to product quality characteristics, e.g. missing or wrong functionality, poor architecture, or inadequate response time. (§5.2.2)

Project risk — a risk related to the management and control of the project, e.g. organizational, people, technical, or supplier issues. (§5.2.2)

Risk — a potential event, hazard, threat, or situation whose occurrence causes an adverse effect, characterized by risk likelihood and risk impact. (§5.2.1)

Risk analysis — the risk management activity consisting of risk identification and risk assessment. (§5.2)

Risk assessment — categorizing identified risks and determining their risk likelihood, risk impact and risk level, prioritizing them, and proposing ways to handle them. (§5.2.3)

Risk control — the risk management activity consisting of risk mitigation and risk monitoring, comprising all measures taken in response to identified and assessed risks. (§5.2.4)

Risk identification — generating a comprehensive list of risks, e.g. via brainstorming, workshops, interviews, or cause-effect diagrams. (§5.2.3)

Risk level — a measure for a risk, expressed via risk likelihood and risk impact; the higher the risk level, the more important its treatment. (§5.2.1)

Risk management — the activities of risk analysis and risk control, which increase the likelihood of achieving objectives, improve product quality, and increase stakeholders' confidence and trust. (§5.2)

Risk mitigation — implementing the actions proposed in risk assessment to reduce the risk level. (§5.2.4)

Risk monitoring — ensuring that mitigation actions are effective, obtaining further information to improve risk assessment, and identifying emerging risks. (§5.2.4)

Risk-based testing — a test approach in which test activities are selected, prioritized, and managed based on risk analysis and risk control. (§5.2)

Test approach — the part of a test plan describing test levels, test types, test techniques, test deliverables, entry/exit criteria, independence of testing, metrics, and test data/environment requirements. (§5.1.1)

Test completion report — a report prepared during test completion summarizing a specific test activity (e.g. test level, test cycle, iteration), including test summary, quality evaluation, deviations, impediments, metrics, unmitigated risks, and lessons learned. (§5.3.2)

Test control — using information from test monitoring to provide, via control directives, guidance and corrective actions to achieve the most effective and efficient testing. (§5.3)

Test monitoring — gathering information about testing, used to assess test progress and measure whether exit criteria (or associated test tasks) are being satisfied. (§5.3)

Test plan — a document describing the test objectives, resources and processes for a test project, documenting the means and schedule for achieving test objectives. (§5.1.1)

Test planning — the test activity of defining the test objectives and selecting an approach that best achieves them within the constraints imposed by the overall context. (§1.4.1, §5.1)

Test progress report — a report generated on a regular basis during test monitoring and control, summarizing the testing period, progress, impediments, metrics, new/changed risks, and testing planned for the next period. (§5.3.2)

Test pyramid — a model showing that different tests may have different granularity, supporting test automation and test effort allocation across test levels. (§5.1.6)

Test strategy — a high-level description of the test approach that a test plan should adhere to, or explain deviations from. (§5.1.1)

Testing quadrants — a model, defined by Brian Marick, grouping test levels with appropriate test types, activities, techniques, and work products according to whether tests are business- or technology-facing, and whether they support the team or critique the product. (§5.1.7)

Chapter 6 — Test Tools

Test automation — the use of tools to facilitate and support test activities such as test management, test design and implementation, test execution, and test coverage measurement; brings potential benefits (e.g., reduced repetitive manual work, greater consistency and repeatability, faster feedback) and potential risks (e.g., unrealistic expectations, vendor dependency, incompatibility with the development platform) that must be weighed before adoption. (§6.1, §6.2)
