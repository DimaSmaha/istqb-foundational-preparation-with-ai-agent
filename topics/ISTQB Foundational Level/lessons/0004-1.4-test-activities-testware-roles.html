1.4 Test Activities, Testware and Test Roles

The densest section in Chapter 1 — the test process, its seven activities, what each one outputs, and who does what.

The test process: seven activities (FL-1.4.1)

These activities often look sequential but are usually done iteratively or in parallel:

  • Test planning — define test objectives, select the approach to achieve them within constraints.
  • Test monitoring and test control — monitoring checks progress against plan; control takes the actions needed to meet objectives.
  • Test analysis — analyze the test basis to identify testable features and define/prioritize test conditions; also evaluates the test basis and test object to find defects and assess testability. Answers "what to test?"
  • Test design — elaborate test conditions into test cases and testware. Answers "how to test?"
  • Test implementation — create/acquire testware for execution: organize test cases into test procedures, build the test environment.
  • Test execution — run the tests, compare actual vs. expected results, log results, analyze anomalies.
  • Test completion — at milestones (release, iteration end, test level completion): archive testware, shut down the test environment to an agreed state, raise change requests for unresolved defects, capture lessons learned, issue the test completion report.

Context shapes the process (FL-1.4.2)

Testing is context dependent (principle 6, §1.3) — the test process is tailored based on:

  • Stakeholders (needs, expectations, willingness to cooperate)
  • Team members (skills, experience, availability)
  • Business domain (criticality, risk, regulations)
  • Technical factors (software type, architecture, technology)
  • Project constraints (scope, time, budget, resources)
  • Organizational factors, the SDLC in use, and tool availability

These factors influence test strategy, technique choice, automation level, required coverage, testware detail, and reporting.

Testware: what each activity produces (FL-1.4.3)

Testware is the output work products of the test activities. Not exhaustive, but the syllabus's own mapping:

  • Test planning → test plan, test schedule, risk register, entry/exit criteria
  • Test monitoring & control → test progress reports, control directives, risk information
  • Test analysis → (prioritized) test conditions, defect reports on the test basis
  • Test design → (prioritized) test cases, test charters, coverage items, test data/environment requirements
  • Test implementation → test procedures, manual/automated scripts, test suites, test data, execution schedule, environment items (stubs, drivers, simulators, service virtualizations)
  • Test execution → test logs, defect reports
  • Test completion → test completion report, action items for improvement, lessons learned, change requests

Traceability (FL-1.4.4)

Traceability is the ability to establish a relationship between the test basis, testware (conditions, risks, cases), test results, and defects. It supports coverage evaluation — e.g. tracing test cases to requirements verifies requirement coverage; tracing test results to risks evaluates residual risk. Good traceability also determines change impact, facilitates audits, supports IT governance, and makes progress/completion reports clearer to stakeholders. It also provides information to assess product quality, process capability, and project progress against business goals.

Two roles in testing (FL-1.4.5)

Test management role

  • Overall responsibility for the test process, team, leadership
  • Focused on: planning, monitoring, control, completion
  • In Agile, some tasks may be handled by the Agile team itself; cross-team tasks by a test manager outside it

Testing role

  • Overall responsibility for the engineering/technical side
  • Focused on: analysis, design, implementation, execution
  • One person can hold both roles at the same time
