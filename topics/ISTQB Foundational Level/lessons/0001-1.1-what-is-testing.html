1.1 What is Testing?

Two misconceptions to unlearn before anything else: testing is not just running the software, and it's not just about checking requirements.

FL-1.1.1 (K1) Identify typical test objectives FL-1.1.2 (K2) Differentiate testing from debugging

What testing actually is

Software testing is a set of activities to discover defects and evaluate the quality of software work products. Those work products, while being tested, are called test objects.

Misconception 1: testing is not only executing tests. Running software and checking results is one activity among several — planning, analysis, design, implementation, execution, and completion (you'll meet all of these in §1.4) — and testing must be aligned with the software development lifecycle (see chapter 2).
Misconception 2: testing is not only verification. Verification checks whether the system meets specified requirements. Validation checks whether the system meets users' and other stakeholders' actual needs in its operational environment. Testing involves both.

Testing can be static (no execution — reviews, static analysis) or dynamic (executing the software). It is not purely technical either: it needs planning, managing, estimating, monitoring, and controlling, and it is largely an intellectual activity requiring testers to have specialized knowledge, use analytical skills, and apply critical thinking and systems thinking — not just running tools.

Typical test objectives (FL-1.1.1)

The syllabus lists these as the typical objectives of testing:

  • Evaluating work products such as requirements, user stories, designs, and code
  • Causing failures and finding defects
  • Ensuring required coverage of a test object
  • Reducing the risk level of inadequate software quality
  • Verifying whether specified requirements have been fulfilled
  • Verifying that a test object complies with contractual, legal, and regulatory requirements
  • Providing information to stakeholders to allow them to make informed decisions
  • Building confidence in the quality of the test object
  • Validating whether the test object is complete and works as expected by the stakeholders

These objectives vary by context: the work product being tested, the test level, risk, the SDLC in use, and business factors like time-to-market.

Testing vs. debugging (FL-1.1.2)

These are separate activities, usually performed by different people:

Testing

  • Triggers failures (dynamic testing) or directly finds defects (static testing)
  • Performed by testers
  • Doesn't fix anything

Debugging

  • Finds the cause of a failure, analyzes it, and eliminates it
  • Performed by developers
  • Typical steps: reproduce → diagnose (find the defect) → fix

When dynamic testing triggers a failure, debugging locates and fixes the underlying defect. Confirmation testing — preferably performed by the same person who ran the original test — then checks the fix worked, and regression testing checks the fix didn't break anything else (both covered fully in §2.2.3). When static testing finds a defect directly, there's no failure to reproduce or diagnose, since static testing cannot cause failures — debugging just removes it.
