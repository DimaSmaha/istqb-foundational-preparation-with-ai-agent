**1. Term-swap (§1.1, §1.2, §1.3):** when an option pairs a familiar word with the wrong partner (verify↔validate, defect↔failure, root-cause↔defect, testing↔QA) — or two concepts share a keyword ("absence of defects") — check which _exact_ concept the option is naming, not whether the sentence sounds plausible. Instance (Exam D·Q1): picked "Validating that legal requirements have been met" as a typical test objective; checking against documented requirements is _verification_, validation is about stakeholder needs in the operational environment. Correct: "Building confidence in the quality of the test object."

**2. Failure is not production-only (§1.2):** a failure is any event where an executed defect makes the system misbehave — on a laptop, in QA, or in production. "Nobody noticed" or "it never left my machine" describes detection or containment, not existence. Instance (live quiz 2026-07-26 Q2): picked "no failure — the unit test ran on a developer machine"; correct was "a failure occurred when the function returned a negative price."

**3. Activity boundary (§1.4):** applying a technique (BVA, EP, etc.) to derive test data or cases is test _design_; analysis only identifies test conditions; implementation only organizes and schedules testware that already exists. Instance (Exam A·Q4, "which is part of test analysis"): picked "using BVA to derive the test data"; correct was "deciding what features and conditions to test."

**4. Shared-X-implies-less-individual-X (§1.5):** "quality is everyone's responsibility" adds a layer of accountability, it doesn't dilute individual accountability. Instance (Exam D·Q7): picked "decreased individual accountability for quality" as a whole-team advantage; correct was "improved communication between team members."
